# Security Policy

Kinney Software Solutions LLC — `reconciliation-platform`

This document covers how to report a security vulnerability in this project and
what to expect afterward. For change-control policy — issues, branches, pull
requests — see [`CONTRIBUTING.md`](CONTRIBUTING.md).

## Reporting a vulnerability

**Do not open a public issue for a security vulnerability.**

Report privately through one of these channels:

1. **GitHub private vulnerability reporting** (preferred) — from this
   repository, go to the **Security** tab and choose **Report a vulnerability**.
   This creates a private advisory visible only to maintainers.
2. **Email** — `security@kinneysoftware.com`

> Replace the address above with a monitored mailbox before publishing this
> file, and enable private vulnerability reporting under
> *Settings → Advanced Security → Private vulnerability reporting* so the
> first channel actually works.

A useful report includes:

- The affected component and version, commit SHA, or deployment
- What an attacker can do — the impact, not only the defect
- Steps to reproduce, ideally minimal
- Any logs, requests, or proof-of-concept you are willing to share

Please report in English. You do not need a working exploit to file a report;
a credible description of the weakness is enough.

## What to expect

| Stage | Target |
| ----- | ------ |
| Acknowledgement of your report | 3 business days |
| Initial assessment and severity rating | 10 business days |
| Status update cadence while open | Every 10 business days |
| Fix or documented mitigation for critical findings | 30 days from confirmation |

These are targets for a small team, not a contractual SLA. If a report is
confirmed as critical and affects processing of customer financial data, it is
treated as an incident and takes priority over scheduled work.

## Disclosure

We ask that you give us a reasonable opportunity to remediate before any public
disclosure, and we will keep you informed of progress rather than leave you
waiting in silence. When a fix ships we are happy to credit you by name or
handle in the advisory, or to keep your report anonymous — your choice.

We do not currently operate a paid bug bounty.

## Supported versions

Only the current release line receives security fixes. Deployments running
older builds should upgrade rather than expect a backport.

| Version | Supported |
| ------- | --------- |
| Current release | Yes |
| Previous releases | No |

## Scope

**In scope** — the application code in this repository, its infrastructure
definitions, its build and deployment workflows, and the dependency manifests
it ships.

**Out of scope** — vulnerabilities in third-party services we consume, which
should be reported to those vendors; findings that require physical access to
a machine or a pre-compromised account; automated scanner output submitted
without a demonstrated impact; and reports about missing hardening headers or
similar with no exploitable consequence.

## Secrets and credentials

This repository has push protection enabled, which blocks commits containing
recognized secret patterns. If a credential nonetheless reaches the repository:

1. **Rotate the credential first.** Assume it is compromised the moment it is
   pushed — history rewriting does not undo exposure.
2. Report it through the private channels above.
3. Only then remove it from history.

Never commit credentials, connection strings, private keys, or customer data —
including in test fixtures, seed scripts, and sample files. Use repository or
environment secrets, or a managed secret store, and reference them at runtime.

Customer reconciliation data must not appear in this repository in any form.
Test fixtures use synthetic data generated by the seed pipeline.

## Development security practices

Controls that apply to every change are defined in
[`CONTRIBUTING.md`](CONTRIBUTING.md). In summary: no direct pushes to protected
branches, every change traceable to an issue, every merge through a reviewed
pull request, and automated dependency and secret scanning on the default
branch.

## Compliance

GitHub's SOC 1 Type 2, SOC 2 Type 2, ISO/IEC 27001, ISO/IEC 42001 and PCI DSS
attestation reports covering the platform hosting this repository are available
to Kinney Software Solutions LLC under our GitHub Enterprise agreement and can
be provided to customers under NDA on request. These cover GitHub as a
sub-processor; they are not an attestation of this application.
