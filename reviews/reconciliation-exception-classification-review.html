Reconciliation Exception Classification Review

Prepared for the reconciliation-platform workspace. Review date: April 5, 2026. Scope: full reconciliation flow from upload and workbook parsing through normalization, matching, exception classification, summary generation, workbook export, API delivery, and web presentation. This rerun reflects the current grouped-residual enhancements and current regression coverage.

Verified finding Recommendation / inferred next step Verified findings are grounded in the current workspace code, docs, and tests. Recommendations are based on the remaining gaps that are visible in the current implementation.

Executive Summary

The project is now materially capable of actionable exception classification. The reconciliation flow is deterministic from parse, normalize, rank, match, classify, summarize, export, and render. It emits accountant-facing categories with rule reasons, evidence, counterpart references, and recommended next actions through the API, workbook export, and web UI.

The most significant improvement since the prior review is that grouped residual cases are no longer taxonomy-only placeholders. The classifier now emits LikelySplitCombineIssue and DepositGroupingIssue from unmatched residual pools, and the test suite exercises those paths end-to-end. The largest remaining gap is architectural: grouped reasoning still happens only after a one-to-one greedy matcher leaves residuals, so support is bounded rather than complete.

Bottom line: the platform has moved beyond generic unmatched reporting and now covers the full required taxonomy at runtime, but grouped categories remain partial because their logic is residual and size-limited rather than native to the matching engine.

Logic and Architecture Assessment

The current design supports clean deterministic classification better than it did in the previous review. Parsing, normalization, matching, classification, summary generation, export, and UI are separated cleanly enough that new categories were added without a broad rewrite.

The main architectural constraint remains the pairwise greedy matcher. It is still the primary decision engine, and grouped reasoning only happens after pairwise consumption has already removed candidates. That means the project now supports grouped categories in practical bounded cases, but not as a general matching capability. The next architectural step should be a staged residual engine that treats timing, grouped split/combine, grouped deposits, miscoding, stale checks, and missing fallback as explicit phases rather than ad hoc tails on top of pairwise matching.

Reporting and Auditability Assessment

The output is actionable for accounting staff. Exception rows expose the category, the originating rule, a human-readable reason, evidence, next actions, and source-row context. The workbook export and UI both preserve accountant-facing labels rather than developer shorthand.

Auditability is also meaningfully improved because summary and detail parity is now asserted across API and workbook output. The remaining auditability risk is completeness of grouped reasoning rather than lack of explanation. When the system chooses a category, it is usually explainable. The harder question is whether a richer grouped or timing category should have been chosen earlier.

Near-Term Enhancements

Title: Turn grouped residual logic into a staged residual engine

Problem observed: Grouped categories work, but only after one-to-one matching and only with a capped residual search.

Why it matters: Some valid grouped scenarios will still be consumed or fragmented before grouped analysis can see them.

Severity: High

Implementation complexity: High

Recommended solution: Preserve the current pairwise matcher for exact and review cases, then introduce an explicit staged residual analyzer that runs grouped searches before final missing fallback with configurable pool size and search bounds.

Impacted files/modules: packages/core/src/matching/engine.ts, packages/core/src/reporting/exceptionClassifier.ts, packages/domain/src/types.ts, packages/config/src/default-config.ts

Change type: Architectural, logic, data model, test coverage

Suggested acceptance criteria: Grouped cases can be traced to a dedicated staged decision family and support configurable search depth without breaking current pairwise regressions.

Title: Strengthen transaction-type evidence across all residual categories

Problem observed: Transaction-kind inference now exists, but its evidence is strongest in grouped and timing cases and weaker elsewhere.

Why it matters: Consistent transaction-type evidence improves deterministic separation between timing, miscoding, grouped receipts, stale checks, and missing items.

Severity: Medium

Implementation complexity: Medium

Recommended solution: Make transaction-kind compatibility or conflict a first-class field in rule traces for timing, grouped, stale-check, and miscoding classifications.

Impacted files/modules: packages/core/src/reporting/exceptionClassifier.ts, packages/domain/src/types.ts, docs/reconciliation-rules.md

Change type: Logic, data model, documentation, test coverage

Suggested acceptance criteria: Each residual exception family explicitly reports type evidence or type conflict in a stable rule-trace structure.

  • Collapse legacy special-case reporting logic into general rule-driven reconciliation behavior.

Suggested Rule Model

  1. Exclude rows and classify invalid or missing data first.
  2. Detect same-source duplicates before any cross-source matching.
  3. Resolve deterministic one-to-one exact matches.
  4. Resolve one-to-one review cases such as reference variance, description variance, amount variance, and ambiguity.
  5. Run residual timing analysis on unmatched pools.
  6. Run residual grouped split/combine analysis.
  7. Run residual grouped deposit analysis.
  8. Run likely miscoding analysis on distinctive same-amount near-date contextual conflicts.
  9. Run stale outstanding check analysis for aged unmatched QBO check-like disbursements.
  10. Fall back to MissingFromQBO and MissingFromBank only after stronger deterministic categories are exhausted.

The current implementation approximates this decision order already, but grouped support remains bounded because it is residual and size-limited. A future redesign should make this order explicit in a staged engine rather than distributed across pairwise matching and classifier tail logic.

Testing Recommendations

  • Add fixtures where grouped candidates exceed the current three-item grouped-side limit so the bounded behavior is intentional and visible.
  • Add targeted regressions for transaction-kind conflicts between deposit-like, transfer-like, and withdrawal-like residuals.
  • Keep API integration tests asserting parity across exception endpoint output, workbook Error Report counts, and summary.countsByCategory.
  • Add regression fixtures that prove 5703 summary behavior never drifts from final classified detail.
  • Add UI tests verifying grouped evidence and next actions remain visible when grouped categories are present.

Closing Assessment

The project now satisfies the core goal of turning reconciliation failures into meaningful accountant-facing categories instead of a generic unmatched dump. The current implementation is auditable, test-backed, and materially stronger than the prior review baseline. The next evolution is not to invent more categories, but to make grouped and timing reasoning first-class matching stages so bounded residual heuristics become a general capability.
